2026 ML & AI

Triton Inference Kernels

When something ran 20× slower, I found the real cause: how the compiler handled the older GPU, not the code. That's the kind of root-cause answer customers need, and I also documented the environment failures publicly.

  • Wrote Transformer inference kernels (softmax, RMSNorm, tiled GEMM) from scratch in Triton, sustaining 82% of peak HBM bandwidth on A100 (72% on T4) and 96% of cuBLAS FP32 throughput with a single unchanged source across both GPU generations; validated against PyTorch on non-power-of-two shapes.
  • Diagnosed a 20× FP16 GEMM slowdown down to the instruction level by dumping compiled PTX: Triton emitted zero tensor-core (mma) instructions on sm_75 vs. 8 on sm_80, confirming a compiler codegen gap (not kernel code) that produced a 30× jump (2.4 → 73 TFLOP/s) on identical source across GPU generations.
  • Built a cross-vendor benchmark suite (roofline analysis, median-of-N timing, FP32/FP16) spanning T4, A100, and AMD MI300X cloud instances; documented Ampere's silent TF32 default breaking bit-level FP32 reproducibility and a full failure taxonomy of ROCm environment provisioning in a public friction log.

Inference Kernel Optimization Lab

Shows I can run a fair comparison and report reproducible numbers, which is what a credible proof of concept depends on.

  • Implemented Transformer inference kernels (GEMM, Softmax, LayerNorm) in a three-tier progression — pure Python baseline, NumPy/BLAS, and JIT-compiled Numba — achieving a ~300× speedup over baseline through cache-block tiling, matrix-transpose memory layout optimization, 4-way loop unrolling, and thread-level parallelism.
